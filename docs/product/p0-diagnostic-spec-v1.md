# Vibe Release V2 — P0 Diagnostic Spec V1

Дата: 17.08.2026
Статус: продуктовая спецификация до реализации.
Цель: спроектировать бесплатный вход Vibe Release, который за ≤2 минуты определяет стадию клиента, даёт полезный результат до заявки и ведёт к правильному платному маршруту.

## 0. Источник механик

### FACT — что подтверждено у сильных конкурентов
- AVAT: быстрый калькулятор `тип → сложность → опции → цена/срок`, бесплатный 30-минутный аудит и 2–3 варианта решения.
- MKDGRUPP: бесплатный конкретный артефакт до оплаты — КП + дизайн-концепт + оценка.
- AxonBuild: 12 коротких readiness areas → estimated score → weakest areas → priority fix prompts; без аккаунта/карты.
- SecurityWall: self-service checklist, прогресс/score, no signup/email; платный слой начинается там, где self-check не может доказать реальное поведение.
- VibeAudit: authorization gate перед active checks; CONFIRMED только при read-only proof; exact fix + re-scan.
- ScanVibe / VibeShield / Revibed: URL-first вход, score/grade, fix prompts, re-scan, history/monitoring как следующий слой.

### DECISION — что делаем у нас
Не делаем один универсальный опрос, который притворяется точной диагностикой для всех. Сначала пользователь выбирает стадию, затем получает соответствующий результат:

1. `IDEA` — есть идея, продукта ещё нет.
2. `STUCK` — продукт уже начат, но человек застрял.
3. `READYISH` — продукт работает или почти работает и готовится к реальным пользователям/данным/платежам.

У каждой ветки свой результат. Только `READYISH` получает предварительный readiness score 0–100. Для идеи и застрявшего проекта числовая «готовность» была бы ложной точностью.

# 1. UX-контракт всей бесплатной диагностики

## Экран 1 — Stage Selector

Заголовок:
**На каком этапе ваш продукт?**

Подзаголовок:
**Выберите текущую ситуацию — за 1–2 минуты покажем следующий разумный шаг. Без карты и регистрации.**

Три карточки:

### A. Есть только идея
Описание: `Понимаю, что хочу получить, но продукта ещё нет.`
CTA: `Разобрать идею`

### B. Уже начал, но застрял
Описание: `Что-то уже собрано с AI/разработчиком, но дальше не получается.`
CTA: `Понять, как довести`

### C. Почти готов / уже работает
Описание: `Проект запускается, но нужно понять, можно ли пускать реальных пользователей, данные и деньги.`
CTA: `Проверить готовность`

### Общие правила экрана
- регистрация не нужна;
- email/телефон/Telegram не спрашиваем до результата;
- прогресс показывается только после выбора стадии;
- пользователь всегда может вернуться и сменить ветку;
- не используем слова «аудит безопасности» как универсальный продукт;
- не обещаем «все ошибки» или «100% безопасность».

# 2. Ветка IDEA — «Есть только идея»

## Цель
За ≤90 секунд получить достаточно данных, чтобы:
1. определить тип продукта;
2. определить базовую сложность;
3. показать 2–3 реалистичных маршрута реализации;
4. сформировать бесплатный mini-scope;
5. после выдачи value предложить передать заявку менеджеру.

## Экран A1 — Тип продукта
Вопрос: **Что хотите создать?**
Один выбор:
- Лендинг / сайт
- SaaS / веб-сервис
- Telegram-бот
- AI-ассистент / AI-агент
- Автоматизация / интеграция / парсер
- Личный кабинет / CRM / внутренний сервис
- Мобильное приложение / PWA
- Другое

Логика: механика близка к AVAT — сначала выбирается тип результата, а не технология.

## Экран A2 — Главная ценность
Вопрос: **Что продукт должен делать в первую очередь?**
Выбор до 2 пунктов:
- Собирать заявки / лиды
- Принимать оплату / подписку
- Давать пользователю личный кабинет
- Автоматизировать ручную работу
- Работать с AI / данными / документами
- Связывать несколько сервисов между собой
- Давать аналитику / отчёты
- Другое

## Экран A3 — Кто будет пользоваться
Вопрос: **Кто будет пользоваться продуктом?**
- Только я / моя команда
- Клиенты без аккаунта
- Клиенты с аккаунтами
- Несколько ролей: клиент / менеджер / админ и т. п.
- Пока не знаю

## Экран A4 — Платежи
Вопрос: **Нужно принимать деньги внутри продукта?**
- Нет
- Разовая оплата
- Подписка / регулярные платежи
- И разовые, и подписка
- Пока не знаю

## Экран A5 — Интеграции
Вопрос: **С чем продукт должен быть связан?**
- Ни с чем внешним
- 1 внешний сервис
- 2–3 сервиса
- 4+ сервисов
- Не знаю

Подсказка: `CRM, Telegram, ЮKassa, email, 1С, API, базы данных и т. п.`

## Экран A6 — AI
Вопрос: **AI должен быть частью продукта?**
- Нет
- Чат / помощник
- Работа с файлами / базой знаний / RAG
- AI-агент, который сам выполняет действия
- Генерация текста / изображений / данных
- Пока не знаю

## Экран A7 — Срок
Вопрос: **Когда нужен первый рабочий результат?**
- Как можно быстрее
- До 2 недель
- До месяца
- Срок гибкий

## Экран A8 — Свободное описание, опционально
Поле до 500 символов:
**Одним абзацем: что должен уметь продукт?**

Не блокирует получение результата.

## IDEA — внутренняя оценка сложности

Это НЕ readiness score. Это только routing/estimation index.

`complexity_points`:

### База по типу продукта
- Лендинг / сайт = 1
- Telegram-бот = 2
- Автоматизация / интеграция = 2
- AI-ассистент = 3
- Личный кабинет / CRM = 3
- SaaS / веб-сервис = 4
- Мобильное приложение / PWA = 4
- Другое = 3 до ручной оценки

### Добавки
- клиенты с аккаунтами: +1
- 2+ ролей: +2
- разовая оплата: +1
- подписка: +2
- 2–3 интеграции: +1
- 4+ интеграции: +2
- AI чат: +1
- RAG/файлы: +2
- agentic actions: +3

### Группы
- 1–3: `SIMPLE`
- 4–7: `STANDARD`
- 8+: `COMPLEX`

Важно: пороги — **Vibe Release product decision**, а не рыночная статистика. Они нужны для одинакового routing; до публикации цен к ним отдельно привязывается коммерческая модель.

## IDEA — Result Screen

Заголовок:
**Уже можно наметить первый рабочий вариант**

Блок 1 — summary:
- тип продукта;
- главный пользователь;
- ключевая функция;
- сложность: `Простой / Стандартный / Сложный`;
- ключевые зависимости: auth / payments / integrations / AI.

Блок 2 — **3 маршрута решения**

### Маршрут 1 — Минимальный
`Самая короткая версия, чтобы проверить, нужен ли продукт вообще.`
Показываем:
- что входит;
- что сознательно не входит;
- ориентир срока из конфигурации;
- ориентир цены из конфигурации.

### Маршрут 2 — Рекомендуемый MVP
`Минимум, который уже можно дать первым реальным пользователям.`
Показываем:
- core flow;
- auth/data/payment needs;
- запуск;
- ориентир срока/цены.

### Маршрут 3 — Полный запуск
`Версия с дополнительными функциями, поддержкой и запасом на развитие.`
Показываем:
- дополнительные функции;
- monitoring/backups/analytics;
- ориентир срока/цены.

Правило: один маршрут помечается `Рекомендуем`, но причина должна быть объяснена одним предложением.

Блок 3 — бесплатный mini-scope
Автоматически выдаём:
- `Что строим`;
- `Для кого`;
- `Главный сценарий пользователя`;
- `Что обязательно в MVP`;
- `Что можно отложить`;
- `5 ключевых технических зависимостей/рисков`.

Блок 4 — CTA после value
**Получить точный scope + первый концепт бесплатно**

Форма:
- Имя — обязательно
- Один контакт из трёх обязателен: Telegram / телефон / email
- Комментарий — опционально
- согласие на обработку ПДн

После submit:
- заявка уходит с сайта во внутренний Telegram-канал менеджера;
- вместе с контактом передаётся весь diagnostic context;
- менеджер не спрашивает пользователя заново то, что уже есть в диагностике.

Target pre-sale artifact:
- точный scope;
- 2–3 решения;
- оценка цены/срока;
- первый экран или ключевой user-flow как визуальный/структурный concept.

Публичный SLA не обещаем до операционного smoke-test процесса. Внутренний target: ≤1 рабочего часа.

# 3. Ветка STUCK — «Уже начал, но застрял»

## Цель
Не спрашивать человека «что хотите разработать с нуля». Сначала понять, можно ли безопасно продолжить существующий проект и где именно он остановился.

## Экран B1 — Что уже есть
Вопрос: **Что сейчас существует?**
- Только локальные файлы / прототип
- Есть GitHub/GitLab репозиторий
- Есть staging/test ссылка
- Есть рабочий публичный сайт/приложение
- Не уверен

Можно выбрать несколько.

## Экран B2 — Насколько работает основной сценарий
Вопрос: **Главный сценарий пользователя сейчас работает?**
- Да, от начала до конца
- Частично
- Иногда работает, иногда ломается
- Нет
- Не знаю, как проверить

## Экран B3 — Где застряли
Вопрос: **Что сейчас мешает двигаться дальше?**
До 3 пунктов:
- Ошибки / приложение падает
- Авторизация / роли / доступ к данным
- База данных
- Платежи
- Деплой / домен / сервер
- API / интеграции
- AI работает нестабильно
- UI / мобильная версия
- Скорость / стоимость / лимиты
- AI постоянно «чинит одно и ломает другое»
- Я уже не понимаю код / архитектуру
- Другое

## Экран B4 — Есть ли точка возврата
Вопрос: **Есть версия, к которой можно безопасно вернуться?**
- Да, нормальная история Git / теги / рабочий commit
- Есть backup/копия, но не уверен
- Нет
- Не знаю

## Экран B5 — Где запускается
Вопрос: **Где проект сейчас можно открыть?**
- Только у меня локально
- Test / staging
- Production / публичный URL
- Сейчас вообще не запускается

## Экран B6 — Пользователи и данные
Вопрос: **Есть реальные пользователи или реальные данные?**
- Нет, только тестовые
- Есть реальные пользователи
- Есть реальные персональные/бизнес-данные
- Уже есть и пользователи, и важные данные
- Не уверен

## Экран B7 — Платежи
Вопрос: **Платежи уже подключены?**
- Нет
- Только test mode
- Да, реальные платежи
- Не уверен, как они сейчас работают

## Экран B8 — Доступ для ревизии
Вопрос: **Сможете предоставить временный/read-only доступ к коду и тестовой среде?**
- Да
- Скорее да
- Нет
- Не знаю, как это сделать

## Экран B9 — URL, опционально
Поле:
`https://...`

Подпись:
`На этом этапе URL нужен для контекста. Активные проверки не запускаются без отдельного подтверждения, что вы владелец проекта или имеете разрешение.`

## STUCK — deterministic routing

Не выводим псевдоточный 0–100 score.

Вместо этого определяем один из трёх маршрутов.

### ROUTE B1 — `ДОВЕСТИ`
Условия:
- core flow = работает или частично;
- есть repo/копия;
- есть точка возврата либо она может быть быстро создана;
- нет признака, что проект полностью недоступен/непонятен.

Результат:
**Проект выглядит пригодным для продолжения.**

### ROUTE B2 — `СНАЧАЛА СТАБИЛИЗИРОВАТЬ`
Любое:
- core flow нестабилен;
- нет безопасной точки возврата;
- production уже живой и содержит реальные данные;
- реальные платежи работают, но владелец не уверен в логике;
- AI постоянно ломает ранее рабочие части.

Результат:
**Перед новой разработкой нужно зафиксировать рабочую версию и границы изменений.**

### ROUTE B3 — `НУЖНА РЕВИЗИЯ ПЕРЕД РЕШЕНИЕМ`
Любое:
- проект не запускается;
- нет репозитория/копии и непонятно, что является актуальной версией;
- клиент не понимает архитектуру и не может определить текущий статус;
- доступы/инфраструктура неизвестны.

Результат:
**По анкете нельзя честно сказать «доделываем» или «пересобираем». Сначала нужна короткая техническая ревизия.**

Автоматически НИКОГДА не выдаём `переписать с нуля` без repo-level human review.

## STUCK — Result Screen

Блок 1:
**Ваш маршрут: Довести / Сначала стабилизировать / Нужна ревизия**

Блок 2 — что уже можно сохранить
На основе ответов:
- работающий frontend;
- repo/history;
- staging/prod;
- auth/data/payment components;
- интеграции.

Если данных недостаточно — пишем `не подтверждено`, а не придумываем.

Блок 3 — Top blockers
Максимум 3 пункта из B3 + critical context.

Блок 4 — next-step map
Например:
1. сделать точку возврата;
2. воспроизвести основной сценарий;
3. зафиксировать ошибку/evidence;
4. определить локальный fix или rebuild boundary;
5. после fix — recheck.

Блок 5 — CTA
### Бесплатно
`Получить mini diagnosis + scope` → форма после результата → внутренний Telegram-канал менеджера.

### Платно
Маршрут `FINISH`: ревизия → fixed scope → исправление → recheck → запуск.
Цена не выводится автоматически до отдельной калибровки FINISH economics.

# 4. Ветка READYISH — «Почти готов / уже работает»

## Цель
Воспроизвести сильнейшую механику рынка: короткий self-assessment → estimated score → weakest areas → fix prompts → evidence-grade paid check.

Это НЕ автоматический security scanner. Это прозрачная предварительная оценка по ответам владельца.

## Общая модель ответа на каждый вопрос

Для каждой применимой зоны четыре состояния:

- `VERIFIED` — `Проверяли на практике, есть evidence` → 1.0
- `CONFIGURED` — `Настроено, но отдельно не проверяли` → 0.5
- `UNKNOWN` — `Нет / не знаю / AI сказал, что всё нормально` → 0.0
- `NA` — `Не применимо` → исключается из знаменателя

Подсказка рядом с `VERIFIED`:
`Вы реально воспроизводили сценарий или видели проверяемое доказательство, а не только наличие настройки в коде.`

# 5. READYISH — 12 readiness areas

## C1. Секреты и ключи
Вопрос:
**Проверяли, что реальные API-ключи, токены и пароли не доступны из frontend, публичного репозитория и истории Git?**

VERIFIED example:
`Проверили client bundle + Git history; найденные ключи отозваны/заменены.`

## C2. Вход и сессии
Вопрос:
**Критические сценарии входа реально проверены: login, logout, reset, истечение сессии и админ-доступ?**

NA разрешён только если в продукте вообще нет аккаунтов/закрытых зон.

## C3. Кто видит чьи данные
Вопрос:
**Если есть несколько пользователей, проверяли двумя разными аккаунтами, что пользователь B не может читать или менять данные A?**

VERIFIED example:
`User B → User A READ/UPDATE/DELETE реально возвращает отказ/0 строк.`

NA — только если нет пользовательских аккаунтов/персональных областей.

## C4. Спам, злоупотребления и лимиты
Вопрос:
**Есть и проверены ограничения на login/forms/API/дорогие операции, чтобы один пользователь не мог бесконечно спамить запросами или сжечь лимиты?**

## C5. AI-функции
Вопрос:
**Если продукт использует AI, проверены ограничения на пользовательский input, стоимость, tool actions и то, что LLM не принимает security/payment решения самостоятельно?**

NA — если AI в продукте отсутствует.

## C6. Данные и восстановление
Вопрос:
**Есть backup и вы реально восстанавливали из него тестовую копию?**

Ключевое правило: `backup exists` без restore test = CONFIGURED, не VERIFIED.

## C7. Платежи и доступ после оплаты
Вопрос:
**Если есть платежи, проверяли server-side подтверждение, повторный webhook/retry, двойную обработку и возврат?**

NA — если денег внутри продукта нет.

## C8. Стабильность и ошибки
Вопрос:
**При падении внешнего API/БД/AI пользователь получает контролируемую ошибку, а команда видит лог/причину? Это проверяли?**

## C9. Скорость, лимиты и масштаб
Вопрос:
**Проверяли хотя бы ожидаемую стартовую нагрузку, медленные запросы и лимиты внешних сервисов/AI, а не только один идеальный пользовательский сценарий?**

## C10. Деплой, rollback и alerts
Вопрос:
**После неудачного релиза можно быстро понять, что сломалось, и вернуть рабочую версию? Monitoring/alerts/rollback реально проверены?**

## C11. Зависимости и supply chain
Вопрос:
**Зависимости зафиксированы lockfile, проверяются на известные уязвимости и не обновляются вслепую?**

## C12. Безопасность будущих изменений
Вопрос:
**Есть минимальный набор тестов/CI и понятная структура проекта, чтобы следующий AI-рефакторинг не ломал уже работающие критические сценарии незаметно?**

# 6. READYISH — Score Formula V1

Пусть `v_i ∈ {1, 0.5, 0}` для всех применимых вопросов.

`BaseScore = round(100 × Σ(v_i) / N_applicable)`

Все 12 зон имеют одинаковый базовый вес.

Почему без скрытых весов:
- score должен быть объясним владельцу;
- у нас пока нет собственной большой выборки, которая доказала бы другие веса;
- critical risk обрабатывается отдельными gates, а не непрозрачной математикой.

## Critical Gates

Gate считается применимым по предыдущим ответам/контексту.

### G1 Cross-user data
Если есть 2+ пользователя/роли/персональные данные, C3 critical.

### G2 Payments
Если реальные платежи подключены, C7 critical.

### G3 Secrets
Для публично доступного продукта C1 critical.

### G4 Recovery
Если продукт хранит данные, потеря которых создаёт реальный ущерб, C6 critical.

### G5 Auth/admin
Если есть закрытая зона/admin/roles, C2 critical.

## Preliminary Status

### 🔴 ПРЕДВАРИТЕЛЬНО: ЗАПУСК РИСКОВАН
Если:
- любой применимый critical gate = UNKNOWN; ИЛИ
- BaseScore < 50.

### 🟠 ПРЕДВАРИТЕЛЬНО: ТРЕБУЕТСЯ ПРОВЕРКА
Если:
- critical gates не UNKNOWN, но хотя бы один = CONFIGURED; ИЛИ
- BaseScore 50–84.

### 🟢 ПРЕДВАРИТЕЛЬНО: ВЫСОКАЯ ГОТОВНОСТЬ
Только если:
- BaseScore ≥ 85;
- все применимые critical gates = VERIFIED.

Важно на экране:
`Это self-assessment по вашим ответам, а не подтверждённый статус Vibe Release.`

Только платная evidence-grade проверка может закончиться нашими финальными статусами:
- НЕ ГОТОВ К ЗАПУСКУ
- ОГРАНИЧЕННЫЙ ЗАПУСК
- ГОТОВ К ЗАПУСКУ

# 7. READYISH — Weakest Areas Engine

Алгоритм Top-3:

1. Все critical areas со значением UNKNOWN.
2. Затем critical areas CONFIGURED.
3. Затем остальные UNKNOWN.
4. Затем остальные CONFIGURED.
5. При равенстве — порядок C1→C12.

Показываем максимум 3.

Каждый блок содержит:
- название области;
- текущий статус;
- почему это важно в 1–2 предложениях;
- что можно проверить самостоятельно;
- `Скопировать prompt для AI`;
- label `Не подтверждено Vibe Release`.

# 8. Fix Prompt Generator V1

Prompts не должны говорить AI «просто исправь всё». Каждый prompt обязан содержать:

1. **Контекст** — какая зона проверяется.
2. **Запрет на разрушительные действия** — не менять production/данные без точки возврата.
3. **Сначала evidence** — показать текущую реализацию/файлы/маршруты.
4. **План исправления** — до внесения изменения.
5. **Минимальный patch** — не переписывать несвязанные части.
6. **Test** — как воспроизвести before/after.
7. **Rollback** — как отменить изменение.
8. **Не заявлять PASS без теста**.

### Универсальный skeleton

`Проверь область: {AREA}. Сначала найди текущую реализацию и перечисли конкретные файлы/маршруты/настройки, которые участвуют. Ничего не меняй, пока не покажешь evidence и краткий план. Не трогай production-данные и не выполняй разрушительные команды. После согласованного минимального исправления создай воспроизводимый тест: BEFORE → FIX → AFTER. Если поведение нельзя подтвердить из текущего доступа, напиши "НЕ ПОДТВЕРЖДЕНО", а не делай вывод по наличию кода.`

К skeleton добавляется area-specific test requirement.

### C3 area-specific
`Создай/используй двух тестовых пользователей A и B. Проверь B→A READ, UPDATE и DELETE для защищённых сущностей. Не извлекай реальные чужие данные; используй synthetic/test records.`

### C7 area-specific
`Проверь повтор одного и того же provider event/webhook, retry после неоднозначного timeout, повтор fulfillment и повтор refund. Итоговая бизнес-операция должна применяться один раз.`

### C6 area-specific
`Не считай наличие backup достаточным. Выполни безопасный restore drill в отдельное test окружение и сравни ожидаемые данные/структуру.`

# 10. Optional URL и Authorization Gate

URL можно ввести ДО результата как необязательный contextual input.

Но passive/self-assessment flow не должен запускать active probes автоматически.

Перед любой активной проверкой отдельный gate:

Checkbox:
**Я владелец этого проекта или имею письменное разрешение на его техническую проверку.**

Короткая подпись:
`Активные проверки выполняются только в согласованном объёме и по возможности read-only/non-destructive.`

Без checkbox:
- можно пройти self-assessment;
- нельзя запускать active verification.

Это воспроизводит сильную механику VibeAudit, но в нашей юридической/операционной модели.

# 14. Acceptance Criteria P0

P0 нельзя считать готовым, пока не выполнено всё:

### UX
- [ ] stage selector работает без регистрации;
- [ ] каждая ветка проходится за ≤2 минуты при обычном темпе;
- [ ] back/edit answers работает;
- [ ] result появляется до запроса контактов;
- [ ] mobile-first;
- [ ] result не выглядит как fake security certification.

### IDEA
- [ ] 3 routes output;
- [ ] mini-scope generated;
- [ ] complexity routing deterministic;
- [ ] price/time config отделена от UI и может меняться без переписывания логики.

### STUCK
- [ ] route = FINISH / STABILIZE / REVIEW deterministically;
- [ ] автоматизация не советует rebuild без human review;
- [ ] critical context real users/data/payments учитывается.

### READYISH
- [ ] 12 areas;
- [ ] VERIFIED / CONFIGURED / UNKNOWN / NA;
- [ ] score formula прозрачна;
- [ ] critical gates override green status;
- [ ] Top-3 deterministic;
- [ ] prompts содержат evidence + rollback + recheck;
- [ ] self-assessment всегда маркирован preliminary.

### Leads
- [ ] контакт спрашивается только после value;
- [ ] один из Telegram/phone/email обязателен;
- [ ] consent recorded;
- [ ] заявка попадает во внутренний Telegram-канал;
- [ ] diagnostic context приходит менеджеру целиком.

### Safety / trust
- [ ] active checks не стартуют без authorization checkbox;
- [ ] no destructive testing by default;
- [ ] no promise «100% secure»;
- [ ] final READY status не выдаётся из self-assessment.

### Analytics
- [ ] все funnel events отправляются;
- [ ] можно посчитать conversion отдельно по 3 стадиям.

1. URL passive scan;
2. 44-check expanded checklist;
3. saved results/history;
4. read-only GitHub connect;
5. re-scan history;
6. client progress dashboard.
