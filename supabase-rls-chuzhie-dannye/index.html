Supabase RLS: как запретить пользователю видеть чужие данные

Работающая авторизация ещё не гарантирует изоляцию данных. На собственном тестовом проекте мы проверили сценарий с двумя пользователями и получили доступ второго пользователя к записи первого.

ТЕСТОВЫЙ ПРОЕКТSupabase

Что произошло

Создали две отдельные пользовательские сессии: пользователь A владеет записью, пользователь B не должен иметь к ней доступа. Под сессией B повторили чтение, изменение и удаление записи A.

ДО ИСПРАВЛЕНИЯ 1 / 1 / 1 чтение / изменение / удаление чужой записи
→
ПОСЛЕ 0 / 0 / 0 чужих строк затронуто

Этот результат относится только к нашему тестовому сценарию. Он не означает, что любая конфигурация Supabase имеет такую же проблему.

ПОЧЕМУ ТАК ПРОИСХОДИТ

RLS отвечает за то, какие строки базы доступны конкретному запросу.

В Supabase таблицы, доступные через Data API, защищают правила Row Level Security. Если правило разрешает слишком широкий доступ или неправильно связывает строку с текущим пользователем, сама успешная авторизация не спасает от доступа к чужим данным.

01

Есть пользователь

Человек успешно вошёл в аккаунт и получил собственную сессию.

02

Есть запись другого

В базе существует строка, владельцем которой является другой пользователь.

03

Есть запрос

Проверяем не интерфейс, а фактический ответ базы под JWT второго пользователя.

04

Есть политика

Именно правило доступа должно оставить B только его собственные строки.

КАК ИСПРАВИЛИ В ТЕСТЕ

Связали доступ с владельцем записи.

В нашем тестовом сценарии условие политики проверяло соответствие текущего пользователя владельцу строки через auth.uid() и поле user_id. После изменения мы не остановились на просмотре SQL — повторили исходные запросы под пользователем B.

Важно проверить не только запрет

Если после «исправления» чужие данные недоступны только потому, что перестало работать вообще всё, задача не решена. Поэтому дополнительно проверили нормальный сценарий владельца: пользователь B по-прежнему мог читать собственную запись.

ЧТО ПРОВЕРИТЬ У СЕБЯ

Минимальная проверка изоляции пользователей

ЧТЕНИЕ

Может ли пользователь B получить строку пользователя A напрямую через API.

ИЗМЕНЕНИЕ

Можно ли под B изменить существующую запись A.

УДАЛЕНИЕ

Можно ли под B удалить запись A.

Отдельно проверяй INSERT, роли, Storage и другие таблицы, если они используются в продукте. Один успешный тест не доказывает безопасность всей системы.

ОФИЦИАЛЬНАЯ ДОКУМЕНТАЦИЯ

На что опирается проверка

Supabase рекомендует защищать доступные через API таблицы с помощью RLS и использовать политики, которые ограничивают строки текущим пользователем. Для UPDATE важны как условия доступа к существующей строке, так и проверка нового состояния строки.
